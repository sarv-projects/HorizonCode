## 1. Purpose

This document decides:

1. The **canonical type notation**, identifier scheme, digest scheme and time scheme used by every HorizonCode schema.
2. The **complete schema catalog**: Session, SessionPosture, SessionConfig, Prompt, InputAdmission, ExecutionClaim, Step, StepRecord, Message, Part (seven variants), ToolCall, ToolResult, ToolDeclarationV1, ToolPermission, Plan, Todo, Goal, AgentProfileV1, SubagentSpec, AgentMessage, TeamState, Budget, BudgetReport, Usage, Cost, MemoryRecord (four tiers), SkillManifest, CommandDef, PluginManifest, HookDef, EffectRequestV1, GuardDecisionV1, LeaseV1, EffectReceiptV1, ReconciliationRecordV1, TrustedHostStateV1, WorktreeV1, ArtifactV1, SnapshotV1, CheckpointV1, McpServerConfig, LspServerConfig, ProviderConfig, ModelRef, WorkflowDef, EvalCase, LearnProposalV1, RateLimitPolicyV1.
3. The **relationship model** between those schemas (ER-style diagram + cardinality edges).
4. The **persistence map**: which file, table, journal or content-addressed store owns each schema, and which copy is the state of record.
5. The **config file schema** for `.hz/config` and user config, and the **merge lattice** that guarantees a workspace may only narrow user configuration (ADR-008).
6. The **versioning rule** per schema and the log-compatibility rule for the event-sourced store (ADR-004).

Out of scope: the event type catalog and projector definitions (see `file:///data/home/forge/hzcode/docs/06-events-and-flows.md`), protocol method framing (`file:///data/home/forge/hzcode/docs/07-apis-and-contracts.md`), the concrete on-disk layout and table DDL (`file:///data/home/forge/hzcode/docs/12-sessions-state.md`), and the JSON Schema text of each field (generated by `hz_codegen` from the tables below; this document is the human authority, `hz_codegen` is the machine authority, and a test asserts they agree).

## 2. Rules

Every rule below is individually testable and named by a stable ID. A rule whose enforcement is not yet built says so inline.

### 2.1 Type system and identity

| ID | Rule |
|---|---|
| **D1** | Every durable or wire object MUST be a named versioned schema `<Name>V<major>` where `<major>` is an integer starting at `1`. There MUST be no unversioned durable shape, including internal kernel state. |
| **D2** | `packages/protocol/src/generated/**` and `crates/hz_abi/src/generated/**` MUST be generated by `hz_codegen` from the schema source. Hand-editing a generated file MUST fail CI (`codegen-clean` gate). |
| **D3** | All digests MUST be lowercase hex with an explicit algorithm prefix: `blake3:<64 hex>` for intent, argument, policy, resource, decision, binding and chain digests; `sha256:<64 hex>` for content addresses. A bare or truncated digest MUST be rejected at parse time. |
| **D4** | All identifiers MUST be `<prefix>_<ulid>` using the closed prefix table in §4.2. An identifier from an unregistered prefix MUST be rejected. |
| **D5** | All durable timestamps MUST be `u64` epoch milliseconds UTC, named `*Ms`, and derived from a monotonic-plus-wall-clock source that never moves backwards within a session. Local time MUST NOT appear in a durable record. |
| **D6** | Unknown fields MUST be rejected (`additionalProperties: false`) with exactly one exception: the `extensions` map (`Map<string, JsonValue>`), which MUST NOT be read by any enforcement path. A value read from `extensions` MUST NOT affect authority, cost, settlement, or safety decisions. |
| **D7** | Schema evolution MUST be: additive optional field (allowed, schema revision bumped, `HZ_PROTO` **not** bumped) or removal/rename/type-narrowing/re-meaned field (requires a new major version). Adding a value to a *closed enum that grants authority* (posture, decision, terminal state, capability) MUST be treated as a breaking change and requires a new major version. |
| **D8** | Adding a value to a *non-authority* enum (e.g. `Part.type`, `ArtifactV1.kind`) MAY be an additive change gated by a negotiated feature flag; consumers MUST treat unknown values as `UNKNOWN` and MUST NOT guess a mapping. |

### 2.2 Storage and state of record

| ID | Rule |
|---|---|
| **D9** | The event log MUST be the state of record. Every projection listed in §4.4 MUST be rebuildable from the log alone by `hzcode session reindex [planned]`. |
| **D10** | Every event payload MUST carry `(sessionId, seq, tsMs, type, actor, payload)`; `seq` MUST be gap-free and strictly increasing per session. A gap MUST be treated as corruption and MUST fail closed. |
| **D11** | No projection MAY be the sole source of any fact that affects authority, cost, or settlement. Such facts MUST be recoverable from the log plus the kernel's OwnerLog. |
| **D12** | Kernel-owned durable state (receipts, lease journal, OwnerLog, effect journal, worktree leases, budget journal) MUST live in the kernel's own state directory with owner-only permissions, MUST NOT be written by the TypeScript runtime, and MUST be the authority for settlement. |
| **D13** | Deletion of any record referenced by a receipt MUST be a tombstone (`deletedAtMs`, `deletedBy`) plus tombstone event, never a row removal. Compaction of tombstones MUST preserve the ID and its receipt chain. |
| **D14** | Content-addressed artifacts MUST be verified on read; a digest mismatch MUST refuse the read and MUST raise `hz.error.raised` with code `HZ_ARTIFACT_INTEGRITY`. |

### 2.3 Authority-bearing schemas

| ID | Rule |
|---|---|
| **D15** | The following schemas are **authority-bearing** and MUST be writable only by the kernel (or, for `LearnProposalV1`, only by a human reviewer through `hz.learn.proposal.review`): `EffectRequestV1` (immutable after submit), `GuardDecisionV1`, `LeaseV1`, `EffectReceiptV1`, `ReconciliationRecordV1`, `TrustedHostStateV1`, `SessionPostureV1`, `ToolPermission`, `LearnProposalV1`. A model-originated tool call MUST NOT be able to write any of them, directly or through a plugin, MCP server, workflow or hook. |
| **D16** | `SessionPostureV1` and `SessionConfig` MUST be validated by the kernel before use; the effective posture MUST carry a `digest` that the kernel recomputes. A posture whose digest does not match recomputation MUST be rejected (`HZ_PRECONDITION_FAILED`) and the previous posture MUST remain in force (fail-closed). |
| **D17** | Capability narrowing MUST be structural, not advisory: child `Session` (subagent, team member, job) capabilities MUST be a subset of the parent's, budgets MUST be ≤ the parent's remaining, and the sandbox/network posture MUST be equal or more restrictive. Enforced by the single subagent primitive (ADR-016) and asserted by a boundary test. |
| **D18** | `EffectReceiptV1.terminal` MUST be exactly one of `SUCCEEDED`, `FAILED`, `DENIED`, `UNKNOWN`, MUST be assigned exactly once per `effectId`, and MUST be monotone (no later record may change it). Corrections MUST be new receipts or `ReconciliationRecordV1` rows. |
| **D19** | An effect whose terminal state is `UNKNOWN` MUST NOT be retried, MUST NOT be reported as successful, and MUST have at least one `ReconciliationRecordV1` before the owning session may reach `completed`. |
| **D20** | `GuardDecisionV1` MUST be recomputable: for the same canonical request, `guard::authorize` MUST return the same decision ID and decision. A mismatch found at use time MUST abort the effect as `DENIED` with reason code `denied_by_decision_mismatch`. *(Ancestor evidence: `authorize_effect` recomputes via `guard::authorize` before every artifact effect.)* |
| **D21** | `LeaseV1.maxUses` MUST be `1`. A lease MUST be bound to the exact `argumentsDigest`; a changed argument requires a new decision and a new lease. Lease expiry is evaluated against the kernel clock, never the client clock. |
| **D22** | Every `ToolDeclarationV1` MUST declare exactly one capability ID from the closed registry in `_conventions.md` §5, and every mutating tool MUST declare an observation method. A tool with no observation method MUST NOT be granted mutation authority. |
| **D23** | Every schema that names a secret MUST name a *reference* (keychain handle, vault path, environment-variable name), never the value. A schema field carrying a secret value MUST fail the secret-scan gate. |

### 2.4 Budget, cost and usage

| ID | Rule |
|---|---|
| **D24** | Usage MUST be recorded per step with an explicit `source` (`provider_reported`, `estimated`, `reconciled`); an estimate MUST be marked as an estimate when a provider fails to report. |
| **D25** | Cost MUST never be silently zero. When pricing is unknown for a `ModelRef`, `Cost.uncertainty` MUST be `unknown` and the budget MUST switch to token/step enforcement with an explicit diagnostic, rather than enforcing a fabricated dollar limit. |
| **D26** | A child (subagent, team member, job, workflow step) MUST NOT be able to exceed the parent's remaining budget; on exhaustion the configured `hardStop` applies and a `hz.usage.recorded` event MUST be emitted before the stop. |
| **D27** | Cost rollups MUST reference the same `priceTableRevision` as the underlying `Usage` rows; mixing revisions in one rollup MUST be rejected, and a repricing MUST be a new artifact (ADR-013 local-first: pricing is local and append-only). |

### 2.5 Configuration

| ID | Rule |
|---|---|
| **D28** | Configuration scopes MUST be exactly: `default`, `managed`, `user`, `workspace`, `workspace_local`, `session` (§4.16.2). |
| **D29** | For **authority keys** (§4.16.3) the effective value MUST be the lattice **meet** (most restrictive) across all scopes that may speak, not the last writer. For **presentation keys** the effective value MUST be the last writer. |
| **D30** | A `workspace` or `workspace_local` value that is more permissive than the effective `user` value MUST NOT take effect; it MUST produce a `config.narrowed` diagnostic and an entry in `hzcode doctor`. |
| **D31** | Programs declared by `workspace` or `workspace_local` scope (hooks, plugins, MCP servers, LSP servers, formatters, workflow scripts, custom providers) MUST stay **inert** until a trust decision for that absolute path and content digest exists in the user-level trust store (authoritative copy `$XDG_STATE_HOME/horizon/user.db`, with a reviewable mirror at `~/.config/horizon/trust.json`; layout owned by `file:///data/home/forge/hzcode/docs/12-sessions-state.md`). |
| **D32** | `managed` scope MUST be able to add only `deny` and `ask` outcomes and to remove capabilities. A `managed` document MUST NOT be able to grant, and MUST NOT be able to be overridden by any other scope. |
| **D33** | Configuration MUST be loaded and merged deterministically: the same scope contents MUST produce byte-identical effective config and the same `effectiveConfigDigest`, which MUST be recorded in the session posture. |

### 2.6 Memory and learning

| ID | Rule |
|---|---|
| **D34** | `MemoryRecord` MUST NOT contain any capability, permission, posture or policy field — structurally, not by convention. A schema test MUST assert this for all four tiers. |
| **D35** | Promotion `episodic → semantic` MUST require (a) provenance linking to source events and receipts, and (b) `reviewState` transition performed by a human principal or an explicit user setting. `working` memory MUST NOT be promoted directly to `semantic`. |
| **D36** | Every `MemoryRecord` MUST carry `provenance` (source session, observed time, evidence refs, confidence) and a `redaction` outcome. A record that failed redaction MUST NOT be persisted. |
| **D37** | `LearnProposalV1.authority.widensAuthority` MUST be `false` for every valid proposal. A validator MUST reject any proposal whose payload targets policy, posture, capability, trust, or the kernel, and MUST record the rejection as a receipted `hz.learn.proposal.created` refusal. |
| **D38** | Applying any `LearnProposalV1` MUST require human approvals (`principal.kind = human`, count ≥ `review.requiredApprovers`) and MUST be revertible through a recorded `rollbackRef`. An agent principal MUST NOT count as an approver. |
| **D39** | Rate limits MUST be expressed as `RateLimitPolicyV1` (§4.9) — one shape, owned here. When several policies match one call, the numeric limit MUST be the **meet** (min) across them, `onExceeded` MUST be the most restrictive, and the policy **reported** in the error MUST be the most specific scope (`budget > provider > principal > workspace > managed`). `HZ_RATE_LIMITED` MUST carry the effective policy id, the window and a truthful `Retry-After`; a limiter MUST NOT keep a second accounting of usage. |

### 2.7 Adopted insertions (RC-15)

> Adopted 2026-11-07 from [29-final-audit.md](./29-final-audit.md) Part D (RC-15).

**1. `ToolResultV1` dual output** (NF-061). Every tool result carries three independently-typed projections of one execution: `machineOutput` (schema-validated, ephemeral, visible to code mode), `content` (durable, model-facing; MUST be non-empty when `machineOutput` is absent), and `metadata` (compact UI JSON, bounded independently — never an unbounded side-channel). **Retention is fail-closed:** a payload too large for managed storage makes the call **fail operationally**; it is never published as a lossy success. Domain output does not change according to model-output bounding policy (bounding happens at the projection, not the record).

**2. `InstructionsStateV1` — value deltas.** Instruction sources are stored as content-addressed blobs; sessions observe `hz.session.instructions.updated {delta, text?}` where "removed" is absence, never a tombstone; an **instruction epoch spans completed compactions**; a fork adopts the parent's newest instruction values as its baseline. Clients display *changed keys*, not privileged prose.

**3. Action↔observation pairing invariant.** A tool observation with no corresponding call, and a call with no observation, are **invalid states** and fail closed: every `hz.part` observation MUST reference its `step.tool.requested` call id; a drained-but-unpaired call is failed at drain start, never replayed, never silently dropped.

### 2.8 Attribution addendum (RC-15)

> Adopted 2026-11-07 from the adoption wave (`30-steal-list.md` §2 E-2; source A.9.4 aider).

- **Commit attribution is a configured, documented truth table.** The `attribute-*` matrix (who is author, who is co-author, what is recorded for tool and assistant contributions) is data with an env-scoped implementation and a docstring-grade specification — AI provenance policy is explicit and reviewable, never implicit in commit text or tooling defaults.

## 4. Data

### 4.1 Type notation

| Notation | Meaning |
|---|---|
| `string`, `bool`, `u32`, `u64`, `i64`, `f64` | JSON: `u64`/`i64` above 2^53 are **canonical decimal strings**, never JSON numbers (matches ancestor `DecimalU64`) |
| `Id` | `<prefix>_<ulid>` (D4) |
| `Digest` | `blake3:<64hex>` or `sha256:<64hex>` (D3) |
| `Sha256` | `sha256:<64hex>` content address |
| `Ms` | epoch milliseconds UTC, `u64` |
| `Seq` | `u64`, gap-free per session stream (D10) |
| `Uri` | `hz://<kind>/<id>` |
| `Path` | absolute POSIX-style path with `/`, NFC-normalized; on Windows a `//?/` UNC prefix is preserved |
| `MoneyMicros` | integer micro-USD (`u64`), never a float |
| `[]T` | JSON array; order is meaningful unless the field name ends in `Set` |
| `T?` | optional (JSON: absent or `null`); an absent field and a `null` field MUST be equivalent |
| `OneOf{a\|b}` | tagged union: exactly one `type` discriminant field |
| `Map<K,V>` | JSON object; keys sorted canonically before hashing |

### 4.4 Cardinality edges and persistence map

### 4.11 Authority schemas (the execution constitution)

These six schemas are the reason HorizonCode exists (README §2, ADR-012). Each is written **only** by the kernel; each is durable; each is citable from a `hz://` URI. The ancestor implements the primitives — the HorizonCode names, envelopes and terminal-state vocabulary are the canonical ones going forward.

Persisted: **kernel** OwnerLog (hash-chained, cursored) plus `hz.db::receipts_index` (read-model index; never authoritative).

**Reconciliation with the wider outcome vocabulary (RC-7).** `_conventions.md` RC-7 fixes one protocol-wide outcome enum: `succeeded | failed | denied | cancelled | budget_exhausted | timeout | interrupted | unknown`. This schema keeps the four **receipt** terminal states (`SUCCEEDED`, `FAILED`, `DENIED`, `UNKNOWN`) because a receipt answers exactly one question — *did the world change, and can we prove it* — and because ADR-012 makes `UNKNOWN` a first-class terminal state. The mapping is total and MUST be applied by the writing component, never by a reader:

| Outcome (RC-7) | Receipt terminal | Condition |
|---|---|---|
| `succeeded` | `SUCCEEDED` | observation present and positive |
| `failed` | `FAILED` | observation present and negative |
| `denied` | `DENIED` | decision was `Deny`; nothing executed |
| `cancelled` | `FAILED` | aborted before dispatch, or a cancellation observation proves no application |
| `cancelled` | `UNKNOWN` | cancellation raced the dispatch and nothing observes the outcome |
| `budget_exhausted` | `FAILED` | refused at a boundary before dispatch |
| `timeout` | `UNKNOWN` | no observation proves non-application (a timeout is precisely the ambiguous case) |
| `interrupted` | `UNKNOWN` | the owner vanished and no probe has run yet |
| `interrupted` | `FAILED` | a probe proves nothing was applied |
| `unknown` | `UNKNOWN` | always |

An effect whose mapping lands on `UNKNOWN` MUST set `reconciliationRequired = true` (D19). A component MUST NOT invent a fifth receipt terminal state to avoid the mapping.

| `experimental` | object | **no** | MUST NOT enable authority changes; an experimental flag that would widen authority MUST be rejected at load |

**4.16.3 The lattice**

Define `a ⊑ b` (“`a` is no more permissive than `b`”) on the authority order: `deny < ask < allow` for decisions, `read-only < workspace-write < danger-full-access` for sandbox mode, `always < on-request < never` for prompting (more prompting is less authority), and `∅ < {capabilities}` by subset for ceilings. The **meet** `⊓` is the greatest lower bound in that order.

| Key class | Operation across scopes | Why |
|---|---|---|
| `permissions[].decision` | `⊓` (meet) per matching rule | `allow ⊓ ask = ask`, `ask ⊓ deny = deny`, `allow ⊓ deny = deny` |
| `sandbox.mode` | `⊓` (most restrictive) | a workspace cannot escalate to full access |
| `sandbox.approvalPolicy` | `⊓` (most prompting) | a workspace cannot silence prompts |
| `sandbox.network.egress` | `⊓` (`none < allowlist < full`) | egress can only be reduced |
| `sandbox.network.allowlist`, `allowPaths`, `envAllowlist`, `envPassthrough` | **intersection** | an allow-list can only shrink |
| `sandbox.denyPaths`, `permissions` deny rules, `hooks` deny outcomes | **union** | a deny list can only grow |
| `budgets.*`, `subagents.maxDepth`, `maxConcurrency`, `budget` limits | **numeric `min`** (`0` = unlimited loses to any finite value) | scarcity can only increase |
| boolean gates (`subagents.enabled`, `mcp.enabled`, `plugins.enabled`, `skills.enabled`, `airGapped`, `telemetry.otel`) | **AND** (for `airGapped`: OR) | a gate can only close |
| `capabilityCeiling` (from profiles/plugins/workflows) | **set intersection** | never widened (D17) |
| `routingPolicy`, `worktree.mode`, `compaction.strategy` | restrictive-end of the documented chain | deterministic, not classifier-guessed |
| presentation keys (`output.*`, `theme`, `keybindings`, `telemetry.endpoint`) | **last writer wins** | cannot widen authority |

Properties the implementation MUST satisfy (property-tested): `⊓` is commutative, associative and idempotent; `x ⊓ x = x`; `x ⊓ default = x` when `x ⊑ default`; and for every authority key the effective value is `⊑` every scope's value. Property tests for these are in §9.

Merge order is fixed: `default → managed → user → workspace → workspace_local → session`. `managed` is applied *before* user but its deny/ask outcomes are stored in a separate, non-removable layer so no later scope can override them (D32). Provenance is recorded per leaf in `SessionConfigV1.sourceOf`.

**4.16.4 Narrowing diagnostics**

Every prevented widening MUST produce a diagnostic record `{path: <absolute config path>, scope: OneOf{workspace, workspace_local}, key: string, requested: JsonValue, effective: JsonValue, reason: OneOf{narrowed_by_user, narrowed_by_managed, requires_trust, not_permitted_in_scope}, atMs: Ms}` that is printed as a warning at startup, returned by `hz.kernel.policy.explain`, and listed by `hzcode doctor`. Silent narrowing is a defect: a user who writes a permission into a repo config must be told it did not apply.

### 4.17 Versioning and migration map

| Layer | Version identifier | Bump rule | Compatibility rule |
|---|---|---|---|
| Client↔agent wire | `HZ_PROTO` (integer, currently `1`) | breaking change to a method, a required field, an error code meaning, or a closed authority enum | additive changes are gated by negotiated feature flags; see `file:///data/home/forge/hzcode/docs/07-apis-and-contracts.md` §4.9 |
| Agent↔kernel | `HZ_ABI` (integer, currently `1`) | breaking change to a kernel operation, envelope, or the handshake | the agent MUST fail closed to read-only mode when the kernel declares an older unsupported ABI |
| Config document | `version` (integer, currently `1`) | removal/rename/re-mean of a key | unknown keys are rejected; the loader refuses to run with an unknown config major and says so |

## 5. Errors & failure modes

### 5.1 Categories

`ErrorCategoryV1` is the ancestor's closed set and is reused verbatim: `Validation`, `Conflict`, `Authorization`, `Capability`, `NotFound`, `Unavailable`, `Deadline`, `Uncertain`, `Corruption`, `Internal`.

### 5.2 Retry classes

`RetryClassV1` is the ancestor's closed set: `Never`, `SafeQueryRetry`, `RetryAfterReconciliation`, `RetryAfterContextRecovery`, `UserActionRequired`, `RetryWithNewId`.

### 5.3 Schema-level error cases

| Condition | Behaviour | Fail closed? |
|---|---|---|
| Unknown field in a durable or wire object | reject with `Validation` / `Never` | yes |
| Unknown value in an authority enum | reject with `Validation` / `Never` | yes |
| Digest mismatch on a recomputed posture, decision or artifact | refuse to use it, raise `HZ_ARTIFACT_INTEGRITY` or `HZ_PRECONDITION_FAILED`, keep the previous valid state | yes |
| `seq` gap or out-of-order event | refuse to project, mark the session `blocked` with `Corruption` / `UserActionRequired` | yes |
| `EffectReceiptV1` terminal state observed twice with different values | treat as corruption, emit `hz.error.raised`, refuse the session's completion | yes |
| `UNKNOWN` receipt with no reconciliation and a completion attempt | refuse completion with `HZ_RECONCILIATION_REQUIRED` / `RetryAfterReconciliation` | yes |
| Budget exhausted mid-step | finish settling the in-flight effect, then stop at the boundary with `HZ_BUDGET_EXHAUSTED` / `UserActionRequired` | no (graceful stop) |
| Config key more permissive than the user scope | ignore the workspace value, record a narrowing diagnostic, continue | no (by design, D30) |
| Untrusted workspace program referenced | stay inert, report `requires_trust`, continue without it | no (by design, D31) |
| Kernel absent / ABI too old | enter `degraded_read_only`: no mutating effect is admitted, reads still work; never fall back to unguarded execution | yes |
| Sandbox dimension unavailable but required | refuse the effect with `HZ_UNKNOWN_DIMENSION` / `Never`, surface the typed residual | yes |
| Plugin signature invalid / API version unsupported | do not load, keep the rest of the session running | yes (for that plugin) |
| Corrupt `StepRecordV1` during replay | abort the replay with `Corruption`, never replay partially | yes |
| Secret detected in a record that should carry only references | refuse the write, raise `Validation`, and the caller must supply a reference | yes |

### 5.4 Degraded modes (explicit, never silent)

The session's app state is one of `full`, `degraded_read_only`, `degraded_unaccounted`, `refused` (`03-hld.md` §6.2), and it is a *visible* projection field, not an internal flag. In `degraded_read_only`: reads, search, context compile and memory recall work; every mutating capability is refused with a reason code rather than a generic error; the TUI shows the reason in the status line; `hz.kernel.status` reports the degradation cause. In `degraded_unaccounted` work proceeds but every receipt carries `accounting: unavailable` (H-41); `refused` fails closed with an explicit reason and a non-zero exit code.

## 6. Flows

### 6.1 Primary flow — from keystroke to receipt and back

1. **Admission.** The front-end calls prompt admission. The orchestrator writes `PromptV1` + `InputAdmissionV1` durably, commits the transaction with `hz.session.prompt.admitted`, and returns the `receiptDigest`. No provider is contacted yet.
2. **Claim.** The runner takes the session's `ExecutionClaimV1` (`held`, `fenceToken` = previous + 1), writes `hz.session.claim.acquired`, and marks the session `busy` (`hz.session.busy.entered`).
3. **Promotion.** At a safe boundary the runner promotes admitted input into a visible user `MessageV1` (same transaction as the promotion event).
4. **Context compile.** The context compiler produces the byte-stable prefix and the projected tail, records a `ContextLedger` entry, and the step records `prefixDigest`/`prefixBytes`.
5. **Stream.** The step issues exactly one `llm.stream`; streamed deltas are transport-only; durable `hz.part.updated` checkpoints freeze parts as they complete (`frozen=true` once `complete`).
6. **Declaration.** Tool calls parse into `ToolCallV1` rows with `origin.kind = SessionBatch`, host-assigned. Unparseable arguments become `parseStatus=invalid` and a model-visible error part — never a guess.
7. **Effect.** For each call in `ordinal` order (parallel within a `parallelGroup` where the declaration allows it): the orchestrator submits an `EffectRequestV1` to the kernel; Guard returns `GuardDecisionV1`; on `Ask` the session enters `waiting_approval` and emits `hz.permission.asked`; on a human answer the decision is re-evaluated with the approval; on `Deny` the call settles `denied` with a reason code. A `deny` MUST NOT emit `hz.permission.asked`: denial is recorded as `hz.effect.decision.made` with its reason code, because no answer could change it (RC-6).
8. **Lease.** On allow, the kernel issues a one-use `LeaseV1` bound to `argumentsDigest`; the host executes inside the confined backend; the kernel observes; the receipt settles as `SUCCEEDED`, `FAILED`, `DENIED` or `UNKNOWN` and chains into the OwnerLog (`hz.effect.settled` / `hz.effect.unknown`).
9. **Projection.** `ToolResultV1` carries the model-facing output plus host `observations`; the step closes its batch, marks parts frozen, and clears `tools_pending`.
10. **Usage and cost.** `UsageV1` and `CostV1` are written per provider call and per billable effect; the session totals update; a threshold crossing emits a budget report.
11. **Next step or stop.** The loop repeats (one stream per step) until `end_turn`, cancellation, budget exhaustion or a fatal error; the claim is released with a terminal outcome.
12. **Verdict.** `hzcode session verify` walks the receipt chain plus the independent-evidence gate: model claims are checked against receipts and observations and can only be **lowered**; an open `UNKNOWN` lowers the verdict and names the reconciliation record; the command prints the verdict, not the model's summary.

### 6.2 Configuration merge flow

1. Discover the scopes in fixed order; parse each with the generated schema; an unknown key or an unknown config major aborts the load with a clear path-qualified error.
2. Apply `default`, then the `managed` layer (deny/ask only), then `user`, `workspace`, `workspace_local`, `session` — each authority key through its lattice operation (§4.16.3).
3. Record per-leaf provenance in `sourceOf`; produce narrowing diagnostics for anything refused.
4. Resolve programs referenced by workspace scope through the trust store; inert entries are reported, not silently enabled.
5. Produce `SessionConfigV1` with `effectiveConfigDigest`; the kernel then validates and issues `SessionPostureV1` with its own digest.
6. Emit the diagnostics to the front-end and to `hzcode doctor`.

### 6.3 Migration flow

1. `hzcode migrate --dry-run` parses the log and projections at the current schema, reports the planned per-major changes and refuses if any session would fail verification afterwards.
2. A real run takes a backup of the state file, applies migrations in one transaction per session, writes receipts for the mutation, and re-runs `session verify`.
3. Generated code (`packages/protocol`, `crates/hz_abi`) is regenerated in the same change and `hz_codegen --check` is part of CI.

## 7. Security & authority

| Capability ID | Where the domain model narrows it |
|---|---|
| `files.read`, `files.write`, `files.patch`, `files.delete`, `files.move` | `EffectRequestV1.resource` + `targetRevision` (CAS) + posture `writablePaths`; a path outside the workspace is `denied_by_resource` |
| `terminal.run`, `process.spawn`, `terminal.pty` | `executable` binding (requested vs host-resolved path + digest + profile digest); broker processes only |
| `net.fetch`, `net.search` | posture `networkPolicy` + `networkAllowlist` intersected through the lattice |
| `providers.infer`, `models.list` | `ProviderConfigV1` allowlist + `ModelRefV1` pinning + `providers.infer` receipts (no un-receipted inference) |
| `memory.read`, `memory.write` | `MemoryRecordV1` carries no capability field (D34) and cannot widen authority; team sync is opt-in |
| `plugins.invoke` | `PluginManifestV1.capabilitiesRequested ∩ sessionCeiling ∩ trustDecision`; each plugin effect is receipted with its inner capability ID |
| `agent.spawn` | `SubagentSpecV1.capabilityGrant` intersection + budget ≤ parent (D17/D26) + receipt linkage |
| `worktree.manage` | `WorktreeV1.capabilityScope` + host-selected `ManagedRoot` origin + receipted lifecycle |
| `secrets.read` | schemas carry keychain/vault references only (D23); a value-bearing field fails the secret-scan gate |
| `session.manage`, `context.manage` | posture and config are kernel-validated; a widening needs an authenticated human and emits `hz.policy.revision.changed` |

Additional model-level rules that carry security weight:

1. **The model can never write an authority schema.** D15 is the load-bearing rule of the whole design; the test for it is a boundary test over every writer of those schemas.
2. **`origin` is host-assigned.** A model batch cannot present itself as `UserAction` (ancestor rule, adopted).
3. **Every schema that names a secret names a reference.** A keychain ref is not a credential; it is a look-up that only the kernel performs.
4. **Evidence cannot be raised, only lowered.** `ToolResultV1.integrityVerdict` and the verify flow can downgrade a claim; no code path lets a model or a plugin raise it.
5. **The learning loop is structurally outside authority.** `LearnProposalV1` has no field that can express a grant, and the validator rejects a payload whose target matches a policy/posture/capability/trust/kernel schema (D37).
