## Rulings 360–361 — authenticated sidecar hashes and single-read receipt linkage (partial R172)

The Rust/TypeScript receipt schema now supports `schemaVersion:2`: a new receipt carrying `effectId`, `postimageDigest`, `postimagePath` or `childEffectIds` hashes those fields into its receipt record and .head anchor. Neither `kernel/src/canon.rs` nor the frozen v1 `hashReceipt` contract was changed. A v1 row remains readable and hash-valid, but its additional `effectId` was not bound to that hash and **cannot** be trusted to identify a child effect: the inspector labels `legacy_unbound_effect_id` instead of displaying it as a verified receipt. A valid v2 row has strict shape checks and refuses duplicate child IDs and unknown fields; the Rust and TS implementations independently verify each other's v2 hashes. The child lookup now reads one receipt JSONL snapshot, hash-walks and checks its anchor, then attributes child effects from the **same snapshot**; duplicate IDs and corrupted anchors refuse. This avoids validation+second-read forgery but does **not** guarantee an OS-level atomic snapshot across writers, authentic human authority, or full nested replay.

Measured: Rust v2 unit **PASS**; Rust release build **PASS**; trusted Rust→TS v2 interop `receipt-schema.test.ts` **4/4 PASS**; combined canonical-event, child-chain, v1/v2, receipt-chain and inspector suites **30/30 PASS**; child-receipt verified-snapshot/inspector suites **11/11 PASS**; TypeScript typecheck PASS; Rust OwnerLog v2-effectId tamper regression **PASS**. All R172 and P0-1 requirements remain OPEN.

## Ruling 357 — nested event stream integrity in receipt inspector (partial R172)

`receipt-child-session-stream.ts` now checks parent session event hash chains and anchors before consuming subagent boundary references, recognizes actual envelope `payload` fields, and independently checks each named child stream. The inspector reports VERIFIED hash+head, legacy unanchored hash walk, INVALID with sequence, or MISSING evidence. It does not fabricate child receipt settlement, provide authenticated provenance for keyless anchors, or replay child effects. Regression tests are `receipt-child-session-stream.test.ts` (valid, tampered parent, tampered child, missing child). Full R172 remains OPEN.

## Ruling 356 — historic direct-file postimage archival (partial P0-2)

Code: `kernel/src/effect_history.rs`; `effect_owner.rs`; additive `effect.owner.postimage.verify.result.history` and `effect.owner.verify` counts in `app/src/contracts.ts`. Existing RPC method names/receipt-v1 hash stay frozen.

1. After a direct kernel file effect independently observes a stable postimage, the kernel rereads all *present* paths twice and compares their bytes to the observed result digest. No caller-provided digest alone can mint historical evidence.
2. Archive uses a 64-MiB per-file bound, owner-only shard permissions on Unix, `create_new` temporary file, data `fsync`, atomic no-clobber hard-link publication, temporary unlink, digest re-read and shard-directory `fsync`. Archive refs and byte lengths are included in the **hashed `owner.settled` event**. Identical content is deduplicated by SHA-256.
3. Snapshot preparation occurs BEFORE `receipt.issue` and `owner.settled`; any archive failure after execution durably records `owner.unknown` and bars later kernel direct mutations, not a forged successful receipt.
4. Historical verification independently reads every archived version, *including superseded versions*, without consulting current workspace disk. Missing/altered blobs show concrete `history.failures`; rows produced before 356 show `legacyUnverifiable`. Deletes and rename-source absence remain `historicalAbsenceFacts`, not byte reconstruction; shell counts as `unsupportedEffects`.
5. `effect.owner.verify` refuses a corrupted postimage archive (without rejecting legacy-only rows solely because snapshots are unavailable). `effect.owner.postimage.verify` preserves its latest-state result and adds `history`; overall `ok` requires both checks to succeed. Fallback Bun still cannot assert Rust OwnerLog verification.

**Security limitations:** This is an archive, not magic recovery of already overwritten historic bytes. A user who controls the kernel state directory can replace both archived data and unkeyed ledger records; keying is optional and outside this slice. State grows monotonically; sensitive file contents are retained under kernel state. Max 64 MiB and Unix filesystem hard-link/fsync support are mandatory for settled new file effects; on an unsupported filesystem, effects fail CLOSED as UNKNOWN, so deployment must verify capabilities first. Archives do not prove external network/process side effects or that a shell was confined.
