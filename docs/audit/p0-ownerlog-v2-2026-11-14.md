## Concrete implementation

### V2 durable prepare → execution boundary and narrow, independently grounded release

`kernel/src/effect_owner.rs` retains a POSIX `flock` over the entire direct Rust
`effect.execute` lifecycle and persists v2 `owner.prepare` and `owner.executing`
records via the fsynced internal, hash-chained OwnerLog. The latter is written **before**
any filesystem or argv primitive can run. The new typed `effect.owner.recover({effectId})`
can release a stranded **v2 prepare-only** record while holding the same lock, after
verifying owner and receipt chains. Recovery writes `owner.released` without executing
the effect; the original effectId remains reserved permanently against duplicate replay.
Status includes `recoverableIds`. All legacy v1 preparations, executing states,
UNKNOWN effects, already settled effects, and tampered logs still refuse clean release.
This is a *narrow* provable clean-release case, not general UNKNOWN remediation.
The debug-only faults `HZ_EFFECT_OWNER_FAULT_AFTER_PREPARE=1` (exit 86) and
`HZ_EFFECT_OWNER_FAULT_AFTER_EXECUTING=1` (exit 87) are injected in separate real
kernel processes, validating recovery/refusal behavior across process death.

### Refusals cannot silently downgrade into another executor

`KernelClient.rpc` now treats a lost `effect.execute` response as **UNKNOWN** and refuses
local replay; once a formerly trusted kernel is lost, subsequent mutating
`executeEffect` requests on the same client refuse. `HZ_EFFECT_HOST_KERNEL=require`
requires a trusted Rust kernel for direct mutating `effect.execute`.
`KernelRefusal` is an explicit typed exported result, and the kernel write/edit/
delete/rename/shell route returns a failed `ToolResult`, not `undefined`, for a
trusted Rust refusal. This prevents `HZ_EFFECT_HOST_KERNEL=default` from downgrading
an explicit OwnerLog UNKNOWN, protected-resource or raw-shell denial into ambient Bun.
The trusted `KernelClient.checkGuard` independently checks the cross-linked OwnerLog/
receipt chain before admitting mutating Guard actions (`fs.write`, `shell.exec`,
`spawn`, `mcp.invoke`, `net.fetch`). If the owner is blocked, corrupted or the
trusted transport was lost, Guard returns a deny. **This is preflight only; a Bun
mutation is not atomically committed or observed under the Rust OwnerLog lock.**

### Stale preimage and patch partial-effect prevention

Direct Rust `fs.write/edit/delete/rename` supports additive
`dispatch.spec.expectedPreimageDigest` as 64-character lowercase SHA-256;
for a new `fs.write`, JSON `null` asserts target absence. The Rust kernel
double-reads the independently observed preimage under its OwnerLog lock **before**
writing `owner.prepare` and repeats the check immediately before the primitive.
A mismatched preimage refuses without an owner intent or disk mutation, so stale
projected `apply_patch`/`ast_edit` changes do not silently overwrite a divergent
file. TypeScript direct routes send preimage pins for readable files.

Multi-projection `apply_patch` (cross-file, same-file multi-hunk, multi-op rename,
or multiple sequential steps) is **refused before any kernel mutation**. The old
code could execute an initial step and then reject another step because every
child step reused the same unique effectId, leaving a partial patch. This
safety change deliberately reduces kernel-route functionality until one atomic
`fs.batch` transaction with independent postimage verification exists.
Single-projection patches retain their current eligible kernel route. A caller
with EffectHost mode `off` can still run Bun-owned patching: that remains a
known architectural bypass, not a completed P0 capability.
